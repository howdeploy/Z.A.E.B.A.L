# Z.A.E.B.A.L. PROTOCOL — LEVEL 4 (Swarm Review)

**False-trigger check — before STOP or auditors.** Installing, configuring or
discussing this skill, quotations and profanity about the outside world are not
swarm requests. Dismiss only a false automatic trigger using the command below;
do not dismiss a substantive complaint or lift an earlier genuine STOP. Explicit
manual invocation skips dismissal, but still requires the launch consent below.

`{{DISMISS_COMMAND}}`

**STOP AND REQUEST CONSENT.** Pause the failing line. Do not launch sub-agents,
external auditors, expensive checks or repairs before the human explicitly
approves the concrete swarm proposal. Reaching L4, `zaebal swarm`, a previous
blanket permission, silence and a streak reset are not approval of this launch.
If the same approved swarm pass is already active, incorporate new evidence
within its scope; do not ask again or launch a duplicate team on each hook.

**Take the initiative.** When complaints reach L4, offer to assemble the swarm
yourself; do not wait for the human to know or type `zaebal swarm`. Ask which
reasoning effort and team setup to use, then obtain explicit launch consent.
MAX effort and the recommended team are choices, never automatic selections.

1. **Read-only preflight.** Identify the project/targets, the entire current diff
   (working tree, index, generated assets/options and relevant commits), available
   recent project sessions, original request, complaints and failed audits. State
   the session time window and gaps. Do not claim unrelated private history is in scope.
2. **Ask the human to choose effort and team setup.** Offer suitable configurations
   of 5–7 reviewers, recommending six: task/history; complete
   diff/provenance; code/architecture/runtime; design/UX/graphics; software/config/
   compatibility; independent falsification and repair/refactoring plan. State
   each role, evidence scope, available tools, supported effort choices (MAX only
   if available), model/vendor options where selectable, concurrency/waves and a
   bounded time/resource budget. Explain the tradeoffs and higher cost; ask which
   effort and setup the human wants and whether to launch that concrete team.
   One explicit response can select both and approve launch; a configuration-only
   answer leaves launch consent pending. Wait; no auditors run meanwhile.
3. **After launch approval only.** Use fresh independent contexts and raw evidence,
   not the working agent's diagnosis. Split the work so the team covers the whole
   declared scope; track files/sessions reviewed and gaps. Use waves if there are
   fewer slots than reviewers. Use the chosen effort and team setup; do not
   silently substitute either. Report unavailable effort/tools or incomplete
   coverage; never pretend a seven-agent team or MAX effort ran when it did not.
4. **Challenge the previous audits.** Reconstruct the first DIVERGENCE POINT and
   map claims/actions to diffs and timestamped commits. Separate WORKING / BROKEN /
   UNKNOWN. Cross-check conflicting conclusions against primary artifacts; agreement
   is not proof. Swarm members are internal; never label them `<zaebal-verdict>`.
5. **Synthesize, then repair within authorization.** Present confirmed causes,
   disputed hypotheses, missed requirements, risks and a concrete fix/refactoring
   plan preserving working behavior. Launch consent alone does not authorize
   refactoring or redesign. Apply fixes only when their concrete scope is already
   authorized or the human approves that plan. Assign one owner per file/asset;
   no competing writers. Run only permitted checks; team consent does not authorize
   tests, UI access, spending, deployment or destructive actions by itself.

Use the skill's `references/swarm-review.md` when available. The short report must
include CONTRACT, DIVERGENCE POINT, FACTS, competing HYPOTHESES, a DISCRIMINATING
CHECK, PREVIOUS AUDIT, WRONG BELIEF (or `not established`), STATUS and OUTCOME GATE,
plus actual coverage, reviewer count/effort and the repair plan. Diagnose before
editing; a diagnosis or proxy test is not a verified fix. Preserve unrelated work.

**Exit.** Finish one bounded swarm pass and deliver the result/handoff. Do not
automatically relaunch another swarm. Keep unavailable verification UNVERIFIED.
An emotional acknowledgment may reset the counter; it does not approve a team,
prove resolution or expand the agreed repair scope. No technical tool lock exists.
